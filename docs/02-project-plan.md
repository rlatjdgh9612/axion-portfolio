## 2. 정보 구조 (IA, Information Architecture)

```
AXION
 ├─ 01. 메인페이지 (Home)
 │     Hero → 프로젝트 미리보기(4개) → About 요약 → 클라이언트 로고 그리드 → Big CTA(Contact) → Footer
 │
 ├─ 02. 소개페이지 (About)
 │     Hero(전용 헤드라인) → 자기소개+핵심역량+핵심스킬 → 업무 프로세스(5 Step) → Big CTA → Footer
 │
 ├─ 03. 프로젝트 페이지 (Works)
 │     Hero(전용 헤드라인) → 필터 탭(전체/인턴/외주/회사) → 전체 프로젝트 리스트(12개) → Big CTA → Footer
 │     └─ 프로젝트 상세 페이지 (개별 URL, 완료 — 워딩은 `06_프로젝트상세페이지_워딩.md` 참고)
 │
 └─ 메뉴 (전체화면 오버레이 패널)
       로고 + 홈/소개/프로젝트 내비게이션
```

### 2-1. 뎁스(Depth) 구조
- **Depth 1**: 메인페이지 / 소개페이지 / 프로젝트 페이지 — 모두 메뉴에서 동일한 뎁스로 접근
- **Depth 2**: 프로젝트 상세 페이지 (개별 URL, 완료 — 11개 구조·워딩 확정)
- **Contact**: 별도 페이지가 아닌 **Big CTA 공통 섹션**으로 전 페이지 하단에 반복 배치 (뎁스 개념 없이 어디서든 도달 가능)

> 설계 의도: 페르소나 B(HR)는 메인페이지만 훑어도 핵심 정보(포지셔닝, 대표 프로젝트 4개, About 요약)를 이미 획득하고, 페르소나 A(실무진)는 소개/프로젝트 페이지까지 들어가 충분한 근거(핵심역량, 업무 프로세스, 전체 프로젝트)를 확인할 수 있음. Contact가 페이지마다 공통 배치되어 있어 어느 페이지에서 이탈하더라도 전환 동선이 끊기지 않음.

## 4. 유저 플로우

### 4-1. 핵심 플로우 A — HR/채용담당자 (빠른 스캔형)
```
[메인페이지 진입]
   → Hero에서 포지셔닝 문구 확인 (3초)
   → 프로젝트 미리보기 4개 스크롤 확인 (10~15초)
   → About 요약 섹션으로 역량 키워드(SERVICE PLANNING 등) 확인
   → Big CTA에서 이메일/전화번호 확인 or 이탈
```

### 4-2. 핵심 플로우 B — 실무진 (심층 검증형)
```
[메인페이지 진입]
   → About 요약 → [더 알아보기] 클릭 → 소개페이지 진입
   → 핵심 역량·핵심 스킬·업무 프로세스(5 Step) 확인
   → 메뉴에서 프로젝트 페이지 이동
   → 전체 12개 프로젝트 스크롤하며 관심 도메인 확인 (핀테크/금융/블록체인 등, 필터 탭으로 유형별 선별 가능)
   → 관심 프로젝트 상세 진입 (구조·워딩 확정 — 06번 문서 참고)
   → Big CTA에서 연락
```

### 4-3. 전환 플로우 (Conversion Flow)
```
[모든 페이지 하단]
   → Big CTA 공통 노출: "채용제안, 협업, 프리랜서 문의까지 언제든 편하게 연락해주세요"
   → 이메일 버튼(mailto) 또는 전화번호 버튼으로 즉시 연결
```

> 01번 분석 문서 2-3의 '전환 문제'를 해결하기 위해, Contact를 별도 페이지로 분리하지 않고 **모든 페이지 하단에 동일하게 배치**하는 것으로 확정 — 어떤 진입 경로로도 전환 동선이 끊기지 않음

11개 클라이언트 프로젝트 상세페이지를 전부 확인한 결과, **기본 골격(7개 대섹션)은 공통이지만 프로젝트 성격에 따라 세부 구성이 달라지는 "가변 템플릿"** 구조로 확인됨.

| 순서 | 대섹션(라벨) | 공통 구성 요소 | 프로젝트별 변형 |
|---|---|---|---|
| 1 | 상세 Hero | Back버튼 / 카테고리 / 프로젝트명 / 태그칩 / 키워드버튼 / 대표이미지 / 메타정보(기간·담당업무%·툴·산출물) | 변형 없음 |
| 2 | Background Overview → 기획 배경 & 문제정의 | 문제정의/핵심과제/프로젝트목표/클라이언트요구사항 4블록 | 변형 없음 |
| 3 | Strategy 또는 Direction → 기획방향 정의 / 디자인 방향 정의 | 소개문구 + 방향성 카드 4개(2x2) | **프로젝트별 확정 라벨**: 대부분 "Strategy/기획방향 정의"를 쓰고, 세무법인 프라이어는 "Direction/디자인 방향 정의" — 프로젝트 성격에 맞춘 의도된 표현으로 채택 |
| 3b | *(지티엑스 전용)* Research → UX 핵심 문제점 분석, 고객사 인터뷰 | 문제점 분석 카드, 인터뷰 인용, 핵심 사용자 페르소나 표, 권한 체계 표 | 안전 인프라 서비스 특성상 **지티엑스에 한해 리서치 근거를 더 두텁게 노출**하는 것으로 확정 (다른 프로젝트로 확대 적용하지 않음) |
| 4 | Structure → 정보구조도(IA) | 소개문구 + IA 표(Depth1/2/3+URL) | 지티엑스는 IA 앞에 "핵심 사용자 유형"·"권한" 표가 추가로 붙음 |
| 5 | Design → 주요화면 | 소개문구 + 그룹별 페이지유형×스크린샷 | **그룹 수가 프로젝트 범위에 따라 다름**: WEB 단일 프로젝트는 "WEB View Design" 1그룹, WEB&Mobile 프로젝트(한국서치펀드·인베스트위드)는 "WEB View Design"+"Mobile View Design" 2그룹, 험블몽은 Tablet/Mobile 반응형까지 별도 노출 |
| 6 | Comparison → 서비스 개선 전/후 비교 **또는** UX 개선 포인트 | — | **신규 구축 프로젝트**: Before/After 이미지 2장 + 불릿 리스트. **리디자인 프로젝트(제이컴퍼니, 인베스트하이브)**: 번호형 리스트 "UX 개선 포인트"(01~06)로 완전히 다른 포맷 사용 |
| 7 | Design System → 디자인시스템 | 로고+컨셉 / 타이포그래피 / 그리드 / 컬러(Primary·Neutral·Semantic) | **프로젝트마다 완전히 독자적**: 폰트 조합 상이(머니가드=Pretendard 단일, 세무법인=Inter+Pretendard+SF Pro 3종, CORE16=Urbanist+Raleway/Pretendard 미사용). **그리드 기준도 다름**: 대부분 Desktop 1920px, 제로에프엔비(PDP, 모바일 커머스)는 **Mobile 375px 기준** |
| 8 | Big CTA / Footer | 공통 컴포넌트 | 변형 없음 |

> **결론**: 상세페이지는 고정된 8단계 템플릿이 아니라, **7개 공통 섹션 + 프로젝트 성격에 따른 조건부 섹션/포맷**으로 설계된 것으로 최종 확인됨. 개발 시 이 가변성을 데이터 모델(7-1)에 플래그로 반영해야 함 (03번 PRD 참고)
> 등급 A/B/C 차등은 여전히 **적용되지 않음** — 다만 위 변형은 "등급"이 아니라 "프로젝트 성격(신규구축 vs 리디자인, 데스크톱 vs 모바일 등)"에 따른 자연스러운 콘텐츠 차이로 해석됨

### 5-5. Big CTA / Contact (전 페이지 공통, 별도 페이지 아님)
- 소제목 + 메인 카피 + 서브텍스트
- 연락 수단: 이메일 버튼(mailto), 전화번호 버튼
- **v1과의 차이**: 이력서 다운로드 버튼은 Big CTA가 아니라 Hero/Footer의 "이력서 다운받기" 버튼으로 별도 존재

## 6. 콘텐츠 우선순위 재검토 (등급 A/B/C 관련) — 최종 확정

v1에서는 프로젝트별로 A(대표작)/B(일반작)/C(참고용) 등급을 나눠 리소스를 차등 배분할 계획이었으나, **11개 전체 분석 결과 등급이 아닌 "프로젝트 성격 차이"로 콘텐츠가 자연스럽게 달라지는 구조**로 최종 확인됨 (5-4 참고).

- **리스트 단계**(메인페이지 미리보기 4개, 프로젝트 페이지 12개): 등급 구분 없이 통일된 카드 템플릿 적용
- **상세페이지 단계**(5-4 참고): 인위적인 등급(A/B/C) 차등은 없으나, **프로젝트 성격에 따른 조건부 섹션/포맷 차이는 존재** — 신규구축 vs 리디자인(Comparison 포맷), 웹전용 vs 웹+모바일(주요화면 그룹 수), 지티엑스의 리서치 심화 섹션 등. 이는 "등급"이 아니라 "콘텐츠 다양성"으로 해석 → **등급 A/B/C 개념은 최종적으로 폐기, 대신 03번 PRD의 `project_type`/`scope_type` 플래그로 관리**

## 7. 확장성 고려 (템플릿화)
